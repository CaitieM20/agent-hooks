Agent Hooks

Agent Hooks is a draft specification for one thing: a stable contract between the software that runs an AI agent (the host) and the controls that govern it (the interceptors).

The main deck covers the problem, interception points, verdicts, interceptor composition, and audit records. After slide 12, the Appendix divider introduces developer reference material.

Spec: AGENT-HOOKS-DRAFT.md §1 Introduction.

The problem

Every agent host and every control integrate differently

Without a common contract, each pairing needs an adapter. The goal: N + M integrations instead of N × M.

Today

N × M bespoke integrations

With Agent Hooks

N + M: one contract on each side

Why a contractAgent Hooks

Every agent framework, runtime, gateway, and harness exposes its own extension points. Every control vendor writes a separate adapter for each one. That's N × M work, and the semantics drift between adapters: what "block" means, what happens on timeout, and what gets logged.

Agent Hooks fixes the contract in the middle. A host implements it once, and an interceptor implements it once.

The host asks for a decision; the interceptor returns a verdict. Next, distinguish that contract from a policy engine, a sandbox, and telemetry.

Interception points

Eight points around the agent loop

Two bracket the session. Six guard every turn: what comes in, each model call, each tool call, and what goes out.

Interception pointsAgent Hooks

The spec fixes eight points with a required order. agent_startup comes first and agent_shutdown last. Each input precedes the model and tool calls it causes, and each pre is paired with exactly one post unless it was blocked.

The tool loop shows that every requested tool is bracketed by pre_tool_call and post_tool_call, and then control returns to the model.

Startup and shutdown can only allow or deny.

Verdicts

Every interceptor returns one of three verdicts

The interceptor returns a decision; the host is responsible for enforcing the decision.

Allow

The action proceeds unchanged.

{ "verdict": { "decision": "allow" } }

An interceptor with nothing to decide still returns allow.

Deny

The action must not proceed.

{ "verdict": {
    "decision": "deny",
    "reason": "email.external_recipient",
    "message": "External email is blocked."
} }

reason is for machines; message is for people.

Transform

The action proceeds with one member replaced.

{ "verdict": {
    "decision": "transform",
»   "transform": { "args": {
      "to": "sam@fabrikam.com",
      "body": "SSN [REDACTED]" } }
} }

Whole-member replacement, validated by the host. Not allowed at startup or shutdown.

VerdictsAgent Hooks

The decision set is intentionally small. Allow proceeds as-is. Deny blocks. Transform proceeds with exactly one member replaced: the bare member for that point, such as args here at pre_tool_call.

Optional members carry the why: a machine reason, a human message, warnings, bounded evidence, and labels. A malformed verdict is treated as a deny with host_error:verdict_invalid.

One tool call, two outcomes

The interceptor only returns a verdict. The host enforces it: it calls the tool, or it blocks the call.

Internal recipient
External recipient
VerdictsAgent Hooks

Same structure as the title slide: the host runs the agent loop, sends a request at an interception point, and gets a verdict back. The new piece is the tool. The host calls it, not the interceptor.

Allow: the agent asks to email an internal recipient. The host pauses at pre_tool_call and sends the request to the interceptor, which returns allow. The host then calls send_email. The result flows through post_tool_call and back to the agent.

Deny: the recipient is external, so the interceptor returns deny with a machine-readable reason such as email.external_recipient. The host must not call the tool and must not emit post_tool_call for it. The agent loop continues as if the action failed, for example by surfacing a tool error to the model, unless the host ends the turn.

The interceptor never touches the tool. Enforcement is the host's job, which is why the verdict is binding rather than advisory.

Illustrative tool, recipients, and reason. Spec: §5.1 Verdict, §6.1 Verdict enforcement, §6.2 Block propagation.

Verdicts

Liftable deny: escalation without an open state

A deny carrying an approval block is denied as-is, unless an approval resolver lifts it.

{ "verdict": {
    "decision": "deny",
    "reason": "email.external_recipient",
    "message": "A manager must approve external email.",
»   "approval": {}
} }
  • Fail closed by construction: unless approved, it's a deny
  • Identity check: a content-derived identity can bind approval to what the approver saw
  • Never consulted at agent_shutdown or in evaluate-only mode
  • Severity aggregation ranks plain deny above liftable deny
  • When the resolver is consulted is set by the composition profile
VerdictsAgent Hooks

Escalation used to be its own decision, which created an in-between state a host had to remember not to proceed from. Now it's a deny with an approval block, so an unhandled escalation is simply a deny.

Step 1: the resolver can approve (an allow substitutes for the deny), reject, or fail to decide. Anything other than approve fails closed with a host_error reason.

Step 2: a host with no resolver enforces it as a plain deny. That's conformant, not an error.

Step 3: the resolution must echo the request's context_identity byte for byte. Content binding depends on the selected identity provider; null echoes null and provides no content-derived replay protection.

Real deployments stack controls: a rate limiter, a redactor, a policy check. The host needs one answer.

This diagram uses parallel/strictest. Severity aggregation ranks deny, liftable deny, transform, then allow. Here the email policy's liftable deny wins. Losing transforms are not applied, including after approval. First-deny and unanimous have their own rules, covered next.

Interceptor Composition

Sequential: each control sees the previous transform

Interceptors run in binding order. In enforce mode, transformed content flows into the next control.

sequential/first_deny

Stop at the first deny; later controls do not run. If approved, on_approval either stops the chain (default) or resumes it.

Use when early blocking is the desired behavior.

sequential/run_all

Continue after interceptor denies. Evaluate all controls in order, then take the strictest verdict.

Use when the full set of control results matters.

Interceptor CompositionAgent Hooks

Order is a product choice: a classifier after a redactor evaluates the replacement, not the original. This fold-through happens only in enforce mode. Evaluation-only validates transforms but leaves later controls on the original input.

First-deny is the default profile, but hosts declare supported profiles and no one profile is mandatory for every host. With on_approval resume, each later liftable deny is consulted in turn. With stop, later controls remain skipped.

Run-all continues after ordinary interceptor denies. A failed fold-transform is the important exception: both sequential profiles short-circuit rather than dispatching an invalid state. Run-all consults approval at most once, only when every deny is liftable.

Spec: §7.2 profiles and defaults, §7.4 Sequential profiles.

Interceptor Composition

Parallel: independent judgments on one snapshot

Every interceptor receives the original request in isolation. No control observes another control's transform.

parallel/strictest

Take the highest-severity verdict. A single winning transform can apply; two or more competing transforms conflict.

on_transform_conflict: deny (default) or seek approval. Approval uses the original, not either replacement.

parallel/unanimous

Allow only when every interceptor allows. Any deny or transform is a disagreement.

on_disagreement: deny (default) or seek approval. Approval does not apply the proposed transforms.

Parallel is an evaluation model, not a scheduling requirement. A host can execute these independent evaluations sequentially or concurrently.
Interceptor CompositionAgent Hooks

Choose snapshot evaluation when controls should independently inspect the same original content. This differs from sequential composition, where a prior transform changes what the next control sees.

Strictest only considers transform conflicts if the severity winner is transform. A deny already outranks those transformations. Even two identical independently proposed replacements count as multiple transforms rather than a merge.

Unanimous treats any non-allow as disagreement. The configured approval path can replace the synthesized disagreement deny; this differs from ordinary severity aggregation. Both parallel profiles dispatch all bound interceptors.

Spec: §7.2 profile model, §7.3 aggregation, §7.5 Parallel profiles.

Appendix · Request and verdictAgent Hooks

The core loop is simple. At a defined point, the host builds a JSON context (here a pre_tool_call for send_email), sends it to the interceptor, and waits.

The interceptor answers with a verdict. Here it's a deny with a machine-readable reason. The host then enforces it: the email is not sent.

The interceptor only returns data. Any change it wants is expressed as a transform verdict, which the host validates and applies.

Interceptors are registered with the host and trusted by it, so registering one is a meaningful grant (§1.4).

Appendix · Scope

What Agent Hooks is not

A narrow contract, deliberately. It says where and how a control decides, not what it decides.

Not

A policy engine

It doesn't define how a verdict is computed. Policy languages, manifests, and lattices belong to interceptor specs such as the Agent Control Specification (ACS).

Policy engines plug in as interceptors.

Not

A sandbox

It constrains a cooperating host inside the trust boundary. No process isolation, no interceptor authentication, no claim of complete mediation.

Conformance is not a security certification.

Not

Telemetry

It's a control plane: every interceptor returns a verdict on the action's path. There's no passive observation, tracing, or metrics interface.

Audit records are a by-product of decisions.

Who builds what

Gateway & harness developers

Build the host side: wire the points, enforce and compose verdicts, and write records. Declare the capabilities your host supports.

Interceptor developers

Accept hook-specific requests and return verdicts. Reuse controls across hosts with compatible capabilities and bindings.

Product & platform owners

Choose which controls run where in a declaration document. Trial them in evaluate-only, then enforce.

Appendix · ScopeAgent Hooks

Three boundaries set expectations early.

Policy: Agent Hooks is the plumbing. How a verdict is computed belongs to interceptor specs. ACS is one example, and any policy engine can sit behind an interceptor.

Security: The host is trusted. The spec constrains a cooperating host and doesn't claim every code path reaches an interception point.

Observability: It's a control plane. Records exist because decisions were made, not as a tracing feed.

Spec: §1.1 Scope, §1.4 Trust model and non-goals.

One session, many turns and tool calls

Startup and shutdown bracket the session. Within it, every turn and every tool call keeps its own interception.

Sessions

Ordered by sequence

  • sequence is unique and strictly increasing; it fixes audit order
  • Multi-turn: many input → output cycles per session
Parallel tool calls

One pair per tool call

  • Each call gets its own pre_tool_call / post_tool_call, paired by tool_call.id
  • A tool can't start until its pre_tool_call verdict is in
  • Stateful interceptors (budgets, rate limits) handle their own concurrency

Appendix · Interception pointsAgent Hooks

Sessions: every request carries a session id and a sequence number. Sequence numbers are unique and strictly increasing, assigned atomically, so records have a total order even under concurrency.

Parallel tools: the contract is per tool call, not per batch. Different calls may interleave. Interceptors that keep state, like rate limiters, own their own synchronization.

The timeline illustrates hook order, not a fixed number of emissions per session. A session can contain many turns. A denied pre-tool call prevents execution and therefore has no post-tool emission.

Appendix · Interception points

Streaming: decide before release, by default

Receiving model tokens and releasing content to a caller are different boundaries. Both need an explicit policy.

Default in enforce mode
Declared alternative

Unbuffered output

Hosts may declare buffered_output: false. A later deny cannot retract content already released.

Optional incremental evaluation

Check prefixes or windows

Declare how much content may be exposed ahead of a verdict. A deny ends the stream; unreleased or unevaluated content cannot persist.

The tradeoff is explicit: latency vs. pre-verdict exposure. Preview channels, observers, and callbacks outside the enforcement boundary count as callers too.
Appendix · Interception pointsAgent Hooks

There are two gates: full model-response assembly before post_model_call, and withholding caller output until the output verdict permits release. An allowed model response can lead to more tools or model calls before final output.

A host may declare unbuffered output. Incremental mediation is a further option: each evaluated prefix or window is an ordinary emission, with a declared exposure bound. Do not equate any unbuffered host with incremental evaluation.

On incremental denial, withhold all content not already released, including previously allowed content still in a buffer. Unevaluated content fails closed at end of stream. These rules also gate durable incorporation.

Spec: §12.1 Streaming model responses, §12.1a Streaming to the caller.

Best-effort cannot bypass

  • The host can't build the context context_invalid
  • Enforced size or depth limits are exceeded

  • Any approval resolver failure
  • An explicit deny, liftable or not

on_error covers only the three failures on the left. Composition and approval keep their own rules.

Verdict configuration optionsAgent Hooks

Three things can go wrong with an interceptor: it throws, it times out, or it returns something that fails validation. By default each becomes a deny with a specific host_error reason, in that interceptor's slot.

Some controls are advisory, so an administrator can set on_error: continue on a binding. The failure then becomes an allow with a control_failed warning. It is recorded, the principal is notified, and the host must disclose it in its conformance claim. Silent continuation is not conformant.

Everything else stays fail closed, whatever on_error says.

Resource limits are host-tunable. The recommended defaults are 5 MiB and 128 nesting levels, not universal conformance thresholds. Breaching an enforced limit must deny with context_invalid, never crash or silently truncate.

Every host must support two modes. In enforce the combined verdict is honored. In evaluate_only the host runs the same interceptors under the same profile and records their verdicts, but proceeds as if the result were allow.

Transforms are still validated, so a broken redactor shows up before you turn it on. The approval resolver is never consulted, so no one gets paged for a dry run. In the record, the enforced identity equals the input identity.

That supports a staged rollout: shadow, review, then enforce. It is not a safety boundary or a perfect simulation of an enforced transform chain. A host selects mode per session or per interception point; a declaration sets configuration.mode.

Spec: §8 enforcement mode, §10.3 record.

Declarative configuration

Configure without code changes

A host declaration is one JSON document an operator owns. It picks which interceptors run, where, in what order, and with which settings.

Declarative configurationAgent Hooks

This is an illustrative declaration behind the end-to-end example. The contoso kinds are fictional registry entries, not built-in interceptors. Only spec and bindings are required; omitted settings use the specification's defaults. An operator's document can omit surface.

Each binding names a kind, which the host looks up in a registry it controls in code. The document can't load code or widen what the host supports.

Loading is a fixed pipeline. Any problem refuses the whole document with a declaration_error class, before any emission and without echoing secrets from config. Nothing is partially applied. Once built, the emitter refuses later reconfiguration, so the declaration is what actually ran.

Hosts that configure in code remain conformant, and records look the same either way.
